## Problem Name

**AI Review Database Schema Mismatch**

## Problem Manifestation

When users attempt to generate AI Review in v0.4.6, the system crashes with the following error:

```
table prompt_reviews has no column named review_schema_version
```

**Error occurs at**:
- User clicks "AI Review" button in prompt view modes
- Backend attempts to save review to database
- SQLAlchemy tries to insert `review_schema_version` field
- SQLite rejects with "no such column" error

**Affected operations**:
- ✅ Frontend UI: Works normally
- ✅ LLM API call: Completes successfully
- ❌ Database insert: Fails with column error
- ❌ AI Review display: Never shown to user

## Root Cause Analysis

### Timeline of Events

1. **v0.4.6 code changes**:
   - `web/db/models.py`: Added `review_schema_version` field to `PromptReview` model
   - `web/db/repository_review.py`: Updated `create_review()` to write schema version
   - Both changes assume the database column exists

2. **Database state**:
   - Local SQLite database (`data/prompt_history.db`) was created in v0.4.5 or earlier
   - `prompt_reviews` table has old schema without `review_schema_version` column
   - `Base.metadata.create_all()` only creates NEW tables, does not ALTER existing tables

3. **Missing migration**:
   - `web/db/database.py` contains `init_db()` function with migration logic
   - Migration logic exists for `prompt_history` table (multiple version updates)
   - **No migration logic exists for `prompt_reviews` table**
   - New field in model + no migration = schema mismatch error

### Why This Wasn't Caught Earlier

- v0.4.6 development likely tested on a fresh database where `create_all()` built tables correctly
- Production/local databases with existing `prompt_reviews` table hit the mismatch
- SQLite does not enforce schema on table creation, only on insert/query

## Fix Details

### 1. Add Migration Logic for `prompt_reviews` Table

**File**: `web/db/database.py`  
**Function**: `init_db()`

Added migration block after existing `prompt_history` migrations:

```python
# v0.4.6 migrations: prompt_reviews table - Add review_schema_version field
if 'prompt_reviews' in inspector.get_table_names():
    review_columns = [col['name'] for col in inspector.get_columns('prompt_reviews')]

    if 'review_schema_version' not in review_columns:
        with engine.connect() as conn:
            # Add new column
            conn.execute(text('ALTER TABLE prompt_reviews ADD COLUMN review_schema_version VARCHAR(50)'))
            
            # Backfill old reviews with legacy version marker
            conn.execute(text("UPDATE prompt_reviews SET review_schema_version = 'v0.4.5_legacy' WHERE review_schema_version IS NULL"))
            
            conn.commit()
```

**Migration behavior**:
1. Check if `prompt_reviews` table exists
2. Inspect table columns
3. If `review_schema_version` column is missing:
   - Add column with `VARCHAR(50)` type
   - Backfill existing rows with `'v0.4.5_legacy'` marker
   - Commit changes
4. If column already exists, skip (idempotent)

### 2. Update Database Module Exports

**File**: `web/db/__init__.py`

Added missing exports for review-related classes:

```python
from .models import PromptHistory, PromptReview
from .repository_review import PromptReviewRepository

__all__ = [
    # ... existing exports ...
    "PromptReview",
    "PromptReviewRepository",
]
```

**Why this matters**:
- `Base.metadata.create_all()` relies on imported models to know which tables to create
- Missing import means `PromptReview` model might not be registered with `Base.metadata`
- Explicit import in `__init__.py` ensures proper module initialization

## Technical Implementation

### Files Modified

1. **web/db/database.py**
   - Added `prompt_reviews` migration block in `init_db()`
   - Migration runs automatically on server startup
   - Idempotent: safe to run multiple times

2. **web/db/__init__.py**
   - Added `PromptReview` to imports
   - Added `PromptReviewRepository` to imports
   - Updated `__all__` export list

### Migration Safety

**Data preservation**:
- ✅ No `DROP TABLE` or `DELETE` operations
- ✅ Existing review data remains intact
- ✅ Only adds new column (non-destructive ALTER TABLE)
- ✅ Backfill uses safe UPDATE with WHERE clause

**Idempotency**:
- ✅ Checks if column exists before attempting ALTER TABLE
- ✅ Safe to run on database that already has the column
- ✅ Safe to run multiple times (no duplicate columns)

**Rollback**:
- If needed, manually remove column: `ALTER TABLE prompt_reviews DROP COLUMN review_schema_version`
- Old code (v0.4.5) will continue working without the column

## Old Review Data Handling

### Legacy Review Markers

Existing AI Reviews (generated in v0.4.5) are marked with:
- `review_schema_version = 'v0.4.5_legacy'`

New AI Reviews (generated in v0.4.6+) are marked with:
- `review_schema_version = 'v0.4.6_calibrated'`

### Outdated Review Detection

**Backend logic** (`web/db/repository_review.py`):
```python
def is_review_outdated(db: Session, history_id: int, current_version: str = 'v0.4.6_calibrated') -> bool:
    review = get_review_by_history_id(db, history_id)
    
    if not review:
        return True  # No review exists
    
    if not review.review_schema_version:
        return True  # Old review without version field
    
    if review.review_schema_version != current_version:
        return True  # Different schema version (e.g., v0.4.5_legacy)
    
    return False  # Review is current
```

**Frontend behavior**:
- GET `/api/history/{history_id}/review` returns `has_review: false, reason: "outdated_schema"` for legacy reviews
- UI shows "Generate AI Review" button as if no review exists
- User can click to regenerate with v0.4.6 calibrated rubric
- Old review data remains in database for historical reference

### Why Not Auto-Regenerate?

We do NOT automatically regenerate old reviews because:
1. **API cost**: Regenerating all reviews would consume significant LLM API credits
2. **User control**: User may not need reviews for old prompts
3. **Lazy generation**: v0.4.5 design already uses lazy generation (only generate when clicked)
4. **Historical data**: Old reviews preserved for comparison/audit purposes

## Prevention for Future Versions

### Process Improvement

When adding new fields to existing tables:

1. **Update model** (`web/db/models.py`):
   - Add new `Column()` definition

2. **Update repository** (e.g., `web/db/repository_review.py`):
   - Add field to CRUD operations

3. **Add migration** (`web/db/database.py`):
   - Add migration block in `init_db()`
   - Check if table exists
   - Check if column exists
   - ALTER TABLE if missing
   - Backfill default values if needed

4. **Update exports** (`web/db/__init__.py`):
   - Ensure all models are imported and exported

5. **Test on old database**:
   - Test with database created in previous version
   - Do not only test with fresh database

### Migration Checklist

- [ ] Model updated
- [ ] Repository updated
- [ ] Migration logic added to `init_db()`
- [ ] Migration is idempotent
- [ ] Backfill logic for old data
- [ ] Module exports updated
- [ ] Tested on old database
- [ ] Tested on fresh database

## Lessons Learned

1. **Always test schema changes on existing databases**, not just fresh ones
2. **Migration logic is required for ALTER TABLE**, not just CREATE TABLE
3. **Idempotent migrations** prevent issues when code is redeployed
4. **Version markers** (like `v0.4.5_legacy`) help track data provenance
5. **Module exports matter** for SQLAlchemy metadata registration
