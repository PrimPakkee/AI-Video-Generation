# v0.4.6.3 Hotfix: AI Review Status/Cache Mismatch and Infinite Loading

**Version**: v0.4.6.3  
**Date**: 2026-05-22  
**Type**: Critical Hotfix  
**Parent Version**: v0.4.6.2  
**Status**: Completed

---

## Problem Name

**AI Review Status/Cache Mismatch and Infinite Loading**

## Problem Manifestation

Users experiencing critical issues with AI Review functionality:

### Symptom 1: Reviews Not Cached After Generation
- User generates AI Review for a topic → Review completes successfully
- User switches to "Raw Text" tab
- User switches back to "AI Review" tab
- **Problem**: System regenerates the review instead of loading from cache
- **Impact**: Unnecessary LLM API calls, 20-30 second wait times for cached data

### Symptom 2: Infinite Loading Spinner
- User clicks "AI Review" button
- UI shows "Generating AI Review..." with spinner
- **Problem**: Spinner never stops, no review ever displays
- Even after waiting 5+ minutes
- Refreshing page doesn't help
- **Impact**: AI Review feature completely unusable for affected topics

### Symptom 3: Switching Topics Regenerates Reviews
- User views Topic A → Generates AI Review
- User views Topic B
- User returns to Topic A → Clicks "AI Review"
- **Problem**: System regenerates instead of loading cached review
- **Impact**: API cost increases, poor user experience

### Symptom 4: Duplicate Review Records
- Database inspection shows multiple review records for same history_id
- Example: `history_id=10` has 3 separate review records
- **Impact**: Database bloat, query confusion, inconsistent state

## Root Cause Analysis

### Critical Bug 1: Query Filter Only Checks `status='active'`

**Location**: `web/db/repository_review.py:30-33`

```python
# OLD BUGGY CODE
def get_review_by_history_id(db: Session, history_id: int):
    return db.query(PromptReview).filter(
        PromptReview.history_id == history_id,
        PromptReview.status == 'active'  # ← BUG: Only queries 'active' status
    ).first()
```

**Problem**:
- v0.4.6.2 introduced status values: `completed`, `generating`, `failed`, `stale`
- v0.4.6.1 and earlier used `status='active'` for completed reviews
- Query filter `status == 'active'` cannot find `status='completed'` reviews
- Result: All successfully generated reviews appear as "not found"

**Impact Chain**:
1. Review generates successfully → saved with `status='completed'`
2. User clicks AI Review again
3. Backend calls `get_review_by_history_id()`
4. Query returns `None` (because status is 'completed', not 'active')
5. Backend thinks no review exists
6. POST endpoint generates new review
7. Creates duplicate database record

### Critical Bug 2: Status Terminology Mismatch

**Problem**: Two parallel status vocabularies exist:
- **Old system** (v0.4.5, v0.4.6.1): `active` = completed review
- **New system** (v0.4.6.2+): `completed` = completed review

**Files affected**:
- `web/db/models.py`: Defines `status` field, no constraints
- `web/db/repository_review.py`: Uses 'active' in queries
- `web/app.py`: Uses 'completed'/'generating'/'failed'/'stale'

**Impact**:
- GET `/api/history/{id}/review` returns `status='none'` for old 'active' reviews
- Frontend thinks no review exists
- POST creates new 'generating' placeholder
- System doesn't recognize existing completed work

### Critical Bug 3: No Migration for Status Values

**Location**: `web/db/database.py:init_db()`

**Problem**:
- v0.4.6.1 added `review_schema_version` field migration
- v0.4.6.2 started using new status values
- **No migration** to convert old 'active' → new 'completed'
- Old reviews remain incompatible with new query logic

**Existing database state**:
```sql

-- Result before fix:
-- active: 4
-- completed: 0
-- generating: 0
```

**Problem**:

- Review stuck with `status='generating'` forever

- Frontend polls indefinitely (up to 5 minutes)
- After 5 min frontend timeout, button still says "generating"
- User can't retry without force refresh

**Impact**:
- Topics permanently stuck in "generating" state
- Database pollution
- User frustration ("Why is it still loading?")

## Fix Implementation

### Fix 1: Rewrite `get_review_by_history_id` to Query All Statuses

**File**: `web/db/repository_review.py`

**Old code** (lines 19-33):
```python
def get_review_by_history_id(db: Session, history_id: int):
    return db.query(PromptReview).filter(
        PromptReview.history_id == history_id,
        PromptReview.status == 'active'  # ← Only queries 'active'
    ).first()
```

**New code**:
```python
def get_review_by_history_id(db: Session, history_id: int, schema_version: str = 'v0.4.6_calibrated'):
    # Get all reviews for this history_id with matching schema version
    reviews = db.query(PromptReview).filter(
        PromptReview.history_id == history_id,
        PromptReview.review_schema_version == schema_version
    ).order_by(PromptReview.updated_at.desc()).all()
    
    if not reviews:
        return None
    
    # Prioritize by status: completed > generating > failed > stale
    status_priority = {'completed': 1, 'generating': 2, 'failed': 3, 'stale': 4}
    
    sorted_reviews = sorted(
        reviews,
        key=lambda r: (status_priority.get(r.status, 99), -r.updated_at.timestamp())
    )
    
    return sorted_reviews[0]
```

**Key changes**:
- ✅ Queries all statuses, not just 'active'
- ✅ Filters by schema_version to avoid v0.4.5_legacy confusion
- ✅ Prioritizes completed reviews first
- ✅ If multiple exist, takes latest by updated_at
- ✅ Handles duplicate records gracefully

### Fix 3: Add Generating Timeout Detection

**File**: `web/db/repository_review.py:get_review_status()`

**Added timeout check**:
```python
def get_review_status(db: Session, history_id: int, current_version: str = 'v0.4.6_calibrated'):
    review = PromptReviewRepository.get_review_by_history_id(db, history_id, current_version)
    
    if not review:
        return 'none'
    
    # Check for generating timeout (>5 minutes)
    if review.status == 'generating':
        from datetime import datetime, timedelta
        timeout_threshold = datetime.utcnow() - timedelta(minutes=5)
        if review.updated_at and review.updated_at < timeout_threshold:
            # Mark as failed due to timeout
            PromptReviewRepository.mark_review_failed(
                db, history_id,
                "AI Review generation timed out. Please try again."
            )
            return 'failed'
    
    return review.status
```

**Behavior**:
- GET endpoint calls `get_review_status()`
- If `status='generating'` and `updated_at` > 5 minutes ago
- Automatically mark as 'failed'
- Return 'failed' status to frontend
- User sees "Try Again" button instead of infinite spinner

### Fix 4: Rewrite `create_or_get_generating_review` Logic

**File**: `web/db/repository_review.py`

**New logic**:
```python
def create_or_get_generating_review(db: Session, history_id: int, schema_version: str):
    # Use fixed get_review_by_history_id (finds all statuses)
    existing = PromptReviewRepository.get_review_by_history_id(db, history_id, schema_version)
    
    if existing:
        # If completed, don't regenerate
        if existing.status == 'completed':
            return (existing, False)  # should_generate=False
        
        # If generating and not expired, reuse it
        if existing.status == 'generating':
            timeout_threshold = datetime.utcnow() - timedelta(minutes=5)
            if existing.updated_at >= timeout_threshold:
                return (existing, False)  # Still valid, don't regenerate
        
        # If failed/stale/expired, reuse this record
        db.query(PromptReview).filter(PromptReview.id == existing.id).update({
            'status': 'generating',
            'updated_at': datetime.utcnow(),
            'review_schema_version': schema_version
        })
        db.refresh(existing)
        return (existing, True)  # should_generate=True
    
    # No existing review, create new placeholder
    review = PromptReview(status='generating', ...)
    db.add(review)
    db.commit()
    return (review, True)
```

**Key changes**:
- ✅ Uses fixed `get_review_by_history_id` (finds completed reviews)
- ✅ Returns existing completed review without regenerating
- ✅ Reuses existing record for failed/stale instead of creating duplicate
- ✅ Only creates new record if none exists

### Fix 5: Update Single Record, Not Batch

**File**: `web/db/repository_review.py`

**`update_review_with_result` - New logic**:
```python
def update_review_with_result(db: Session, history_id: int, review_data: dict, schema_version: str):
    # Find the specific generating review
    review = db.query(PromptReview).filter(
        PromptReview.history_id == history_id,
        PromptReview.review_schema_version == schema_version,
        PromptReview.status == 'generating'
    ).order_by(PromptReview.updated_at.desc()).first()
    
    if not review:
        # Fallback: get any review
        review = PromptReviewRepository.get_review_by_history_id(db, history_id, schema_version)
    
    if review:
        # Update ONLY this specific record (by ID)
        db.query(PromptReview).filter(PromptReview.id == review.id).update({
            'review_json': json.dumps(review_data),
            'total_score': review_data.get('total_score', 0),
            'status': 'completed',
            'updated_at': datetime.utcnow()
        })
        db.commit()
```

**Key changes**:
- ✅ Finds specific record (latest generating for this schema)
- ✅ Updates by `review.id`, not by `history_id`
- ✅ Even if duplicates exist, only updates one
- ✅ Prevents batch overwrite issue

**`mark_review_failed` - Similar fix**:
```python
def mark_review_failed(db: Session, history_id: int, error_message: str = None, schema_version: str):
    # Find specific generating/failed review
    review = db.query(PromptReview).filter(
        PromptReview.history_id == history_id,
        PromptReview.review_schema_version == schema_version
    ).filter(
        (PromptReview.status == 'generating') | (PromptReview.status == 'failed')
    ).order_by(PromptReview.updated_at.desc()).first()
    
    if review:
        # Update by ID only
        db.query(PromptReview).filter(PromptReview.id == review.id).update({
            'status': 'failed',
            'review_json': json.dumps({'error': error_message}),
            'updated_at': datetime.utcnow()
        })
        db.commit()
```

## Handling Duplicate Reviews

**Problem**: Database already contains duplicate review records from previous bugs.

**Query to find duplicates**:
```sql
SELECT history_id, review_schema_version, COUNT(*) as count
FROM prompt_reviews
GROUP BY history_id, review_schema_version
HAVING COUNT(*) > 1;

-- Result:
-- history_id=10, schema=v0.4.6_calibrated, count=3
-- history_id=16, schema=v0.4.6_calibrated, count=2
-- history_id=18, schema=v0.4.6_calibrated, count=3
```

**Solution**: New query logic handles duplicates gracefully
- Prioritizes `completed` status
- Takes latest by `updated_at`
- Only updates one record at a time

**Future prevention**:
- Unique constraint: `UNIQUE(history_id, review_schema_version, status)` (not implemented to avoid complex migration)
- Repository-level checks prevent duplicate creation
- `create_or_get_generating_review` reuses existing records

## Migration Safety

**Idempotent**: Migration can run multiple times safely
```python
UPDATE prompt_reviews SET status = 'completed' WHERE status = 'active';
-- If no 'active' records exist, affects 0 rows (safe)
```

**Non-destructive**: Converts status values, no data deletion

## Known Limitations

1. **Duplicate records not cleaned**: New query handles them, but duplicates remain in database
   - Not a problem for functionality
   - Slight storage waste
   - Could add cleanup script in future version

2. **No unique constraint**: Could prevent future duplicates
   - Would require complex migration (SQLite limitations)
   - Repository-level prevention is sufficient for now

3. **Frontend-only deduplication**: In-flight map is memory-only
   - Lost on page refresh
   - Not shared across browser tabs
   - Backend idempotency is primary defense
