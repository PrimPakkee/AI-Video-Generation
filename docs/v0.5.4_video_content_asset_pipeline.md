# v0.5.4 — Video Content Asset Pipeline

This document describes the v0.5.4 release: the **Video Content Asset
Pipeline** that produces the structured content bundle a future v0.6.0
Seedance integration will consume.

> **v0.5.4 does NOT call Seedance, does NOT call any real video API, does
> NOT generate real mp4, and does NOT download any video file.** It only
> generates structured text/JSON assets and creates a Mock VideoJob shell.

## 1. Goals

- Produce, for every Video Mode topic, a deterministic on-disk **content
  asset bundle** that a real video provider can later consume.
- Reuse Prompt Mode's LLM engineering patterns (env-driven OpenAI client,
  temperature/json_mode fallback, JSON parse fallback) **without copying
  the NotebookLM prompt template**.
- Keep `/api/video/generate` synchronous and never let asset generation
  return a 500 — fall back to deterministic synthetic assets instead.
- Stay strictly behind the v0.5.x boundary: no Seedance, no real provider
  file, no real mp4, no real video URL, no API key written to disk.

## 2. New module — `web/video_asset_pipeline.py`

Public entry point:

```python
build_video_content_assets(
    topic: str,
    output_dir: Path | str,
    history_id: Optional[int] = None,
    llm_client: Optional[Any] = None,
) -> dict
```

Returns a result dict containing at minimum:

| Key | Type | Description |
| --- | --- | --- |
| `success` | bool | True if assets were written. False on hard failure (still returns a fallback bundle). |
| `warnings` | list[str] | Non-fatal warnings (LLM unavailable, JSON parse failed, etc.). Never contains the API key. |
| `video_assets` | dict | Normalized bundle — see §4. |
| `provider_prompt` | str | English provider prompt for the future Seedance call. |
| `provider_request_preview` | dict | Forward-looking request shape. v0.5.4 never sends it. |
| `asset_manifest` | dict | Contents of `generation_manifest.json`. |
| `asset_paths` | dict[str, str] | Absolute paths to each written asset. |
| `preview_text` | str | Plain-text body for the Video Mode Preview tab. |
| `overview_cn` | str | Chinese design summary for the Video Mode Overview tab. |
| `llm_used` | bool | Whether the LLM actually produced parseable JSON. |
| `schema_version` | str | `video_assets_v0.5.4`. |

The pipeline never raises. Any unexpected exception is caught and falls
back to the deterministic synthetic bundle.

## 3. LLM configuration reuse

The pipeline reads the same env vars Prompt Mode uses, so users do not need
to configure two API keys:

- `AI_VIDEO_LLM_PROVIDER` (default `openai_compatible`)
- `AI_VIDEO_LLM_BASE_URL` (default `https://api.openai.com/v1`)
- `AI_VIDEO_LLM_MODEL` (default `gpt-5-chat`)
- `AI_VIDEO_LLM_API_KEY`
- `AI_VIDEO_LLM_TEMPERATURE` (default `0.7`)
- `AI_VIDEO_LLM_MAX_TOKENS` (default `4096`)
- `AI_VIDEO_LLM_TIMEOUT` (default `60`)
- `AI_VIDEO_LLM_RESPONSE_FORMAT` (default `json_object`)

Compatibility chain:

1. Try with `temperature` + `response_format=json_object`.
2. If the API rejects `temperature`, retry without it (still try
   `json_object`).
3. If the API rejects `response_format`, retry without it (still try
   `temperature`).
4. If both fail, retry with neither.

If the API key is missing, the LLM step is skipped entirely and the
deterministic fallback bundle is written. The pipeline **never** prints,
logs, or persists the API key value — only `bool(api_key)` appears in
manifest / debug output.

**Config namespace.** The primary config is `AI_VIDEO_LLM_API_KEY`; the
legacy `OPENAI_API_KEY` is checked only as a low-priority fallback so
existing environments keep working, but reports always use
`AI_VIDEO_LLM_API_KEY configured: true/false` rather than
`OPENAI_API_KEY configured: …` (the latter was misleading). When the
pipeline runs as a CLI (`python -m web.video_asset_pipeline`), it
attempts to load the project root `.env` so standalone, FastAPI, and
stability-check paths see the same configuration.

## 4. Output bundle — `outputs/<slug>/video_assets/`

| File | Format | Source |
| --- | --- | --- |
| `topic_analysis.json` | JSON | `topic_analysis` from LLM (or fallback) |
| `reasoning.md` | Markdown | rendered from `reasoning` |
| `video_script.md` | Markdown | rendered from `script` + `storyboard` |
| `storyboard.json` | JSON | `storyboard` (≥5 scenes) |
| `provider_prompt.txt` | text | English provider prompt for Seedance |
| `provider_request_preview.json` | JSON | forward-looking Seedance request shape |
| `generation_manifest.json` | JSON | schema version, file index, warnings, LLM debug (no key) |
| `llm_raw_output.txt` | text | raw LLM output (only when LLM was reached) |

`generation_manifest.json` is the source of truth for what was generated
and what failed. Its `assets` / `files` lists are self-registering and
include `generation_manifest.json` itself — the core bundle is 7 entries
(8 when the LLM was reached and `llm_raw_output.txt` was written).
Manifest top level also carries `future_provider="seedance"`,
`submit_mode="not_connected"`, and `real_video_generated=false` for
future v0.6.0 Seedance contract alignment.

`provider_request_preview.json` is a **future Seedance contract preview**
— it exposes top-level `provider` / `future_provider` / `prompt` /
`duration_seconds` / `aspect_ratio` / `resolution` / `fps` / `language` /
`style` / `negative_prompt` / `submit_mode` / `provider_status` /
`real_video_generated` / `note`, plus a nested `request` field for
backwards compatibility. **v0.5.4 never sends this request.**

### Required JSON shape (LLM target)

```
{
  "topic_analysis": { topic, normalized_topic, content_type, difficulty,
                      core_concept, target_audience, video_goal,
                      risk_points[], visual_requirements[], language },
  "reasoning":      { correct_answer, step_by_step_reasoning[],
                      common_wrong_intuition, key_teaching_point,
                      accuracy_notes },
  "script":         { hook, narration, on_screen_text[], timing_plan[],
                      ending },
  "storyboard":     { duration_seconds, aspect_ratio, style,
                      scenes[ ≥5 ], negative_constraints[] },
  "provider_prompt": "ENGLISH provider prompt …",
  "web_copy_placeholder": { title, description, hashtags[] }
}
```

Hard constraints embedded in the template AND in the storyboard's
`negative_constraints`:

- single narrator
- monologue narration
- no dialogue / no interview / no podcast / no two-host conversation /
  no multiple speakers
- no irrelevant decorative visuals
- no wrong answer / no unsupported visual claims
- reasoning and visuals must match
- on-screen text must be large and readable

## 5. Backend integration

`web/app.py`:

1. Imports `build_video_content_assets` and `VIDEO_ASSETS_SCHEMA_VERSION`.
2. `/api/video/generate` and `/api/video/history/{id}/regenerate` are
   structured as: **(a)** create the `VideoHistory` record first using the
   subprocess-stage outputs; **(b)** call
   `build_video_content_assets(history_id=record.id, …)`; **(c)** call
   `VideoHistoryRepository.update_asset_pipeline_result()` to write
   `provider_prompt` → `prompt_text`, pipeline preview → `preview_text`,
   pipeline design summary → `overview_cn`, and a JSON blob (schema
   version, asset manifest, asset paths, warnings, llm_used,
   fallback_used, provider status) → `metadata_json`. This order
   guarantees `generation_manifest.json` carries a real `history_id` (not
   `null`) and that all four fields are durable across page refresh.
3. The response always returns the post-write `record.to_dict(include_prompt=True)`
   so the frontend renders the latest values. The response also carries
   `video_assets`, `provider_prompt`, `provider_request_preview`,
   `asset_manifest`, `asset_paths`, `video_assets_schema_version`,
   `video_assets_warnings`, `llm_used`, and a `message` field that reads:
   `Real video provider is not connected in v0.5.4. Content assets were
   generated successfully, but no real video API was called.`
4. Mock VideoJob creation behavior is unchanged from v0.5.3.
5. `/api/video/history/{id}/download-all`:
   - Bundle layout becomes:
     ```
     raw_text.txt
     preview.txt
     overview.txt
     web_copy.txt
     metadata.json
     video_assets/topic_analysis.json
     video_assets/reasoning.md
     video_assets/video_script.md
     video_assets/storyboard.json
     video_assets/provider_prompt.txt
     video_assets/provider_request_preview.json
     video_assets/generation_manifest.json
     ```
   - `metadata.json`:
     - `export_schema_version` upgraded to `video_v0.5.4`.
     - Adds `video_assets_schema_version=video_assets_v0.5.4`.
     - Adds `provider_status=provider_not_configured`.
     - Adds `real_video_generated=false`.
     - Adds `has_video_assets` (bool).
   - The bundle still contains **zero** mp4 / mov / video URL / token /
     API key.

## 6. Frontend integration — Video Mode tab map

| Tab | v0.5.3 | v0.5.4 |
| --- | --- | --- |
| Video | compact VideoJob + player placeholder | unchanged |
| Web Copy | placeholder (editable text) | unchanged |
| Raw Text | NotebookLM script | **`provider_prompt`** (future Seedance input) |
| Preview | parsed sections | **pipeline `preview_text`** (script + storyboard summary) |
| Overview | `overview_cn` from topic.json | **pipeline-rendered Chinese design summary** |
| AI Review | placeholder | unchanged |

Multi-stage progress panel goes from 8 → **9 steps**:

1. Analyzing topic
2. Verifying answer
3. Writing video script
4. Building storyboard
5. Creating provider prompt
6. Preparing provider request
7. Creating mock video job
8. Saving assets
9. Done

## 7. Stability checks

`scripts/run_stability_checks.py` runs the new `check_v054_fixes()` group.
All checks are read-only — they never call an LLM, never modify a
database, never start the service. The group covers:

- `web/video_asset_pipeline.py` exists and exports
  `build_video_content_assets` + `VIDEO_ASSETS_SCHEMA_VERSION`.
- `templates/video_asset_prompt_template.md` exists and contains the v0.5.4
  required keys + hard constraints.
- `web/app.py` imports the pipeline and calls
  `build_video_content_assets(` from both generate and regenerate paths.
- `metadata.json` in `download_all` uses
  `export_schema_version=video_v0.5.4` and includes the v0.5.4 fields.
- `download_all` adds the `video_assets/` folder from disk to the zip.
- `web/static/main.js` declares the 9-step `VIDEO_GENERATION_STEPS` list
  using the v0.5.4 keys.
- The frontend message text references v0.5.4, not v0.5.3.
- No real provider files (`seedance_provider.py`, etc.) exist.
- No `video_reviews` / `video_review` table introduced.
- `CHANGELOG.md` has a v0.5.4 entry with the protection clauses.
- `docs/v0.5.4_video_content_asset_pipeline.md` exists.

## 8. Protection boundary

- No Seedance integration.
- No real video provider implementation file.
- No real video API call.
- No real mp4 generated, no video file downloaded.
- `.env` is not modified; the API key is never printed, logged, or written
  to disk.
- No new async queue (no Celery / Redis / RQ).
- No `video_reviews` table introduced.
- Prompt Mode database schema (`prompt_history`, `prompt_reviews`),
  Prompt Mode generation pipeline, NotebookLM prompt template, and AI
  Review rubric are untouched.
- Prompt Mode capabilities (history / version / favorite / pin / trash /
  Regenerate / Download All) are preserved end-to-end.
- VideoJob and Video Content Asset writes are confined to
  `data/video_history.db` and `outputs/<slug>/video_assets/`.
